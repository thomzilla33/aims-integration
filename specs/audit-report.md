# Design-Token Audit — AIMS-OS Prototypes

_Generated by `scripts/token-audit.js` + structural scan. Scope: the 6 canonical
single-file HTML prototypes in this repo (`aims-os-prototype`)._

## TL;DR

- These are **single-file HTML prototypes** — there are **no `.css`/`.scss` files**.
  All styling lives in inline `<style>` blocks (plus `style=""` attrs and SVG
  `fill`/`stroke`).
- A token layer **already exists and is large**: **1,278** `--token` definitions
  and **5,983** `var(--…)` references across the 6 files. The problem is not
  "no tokens" — it is *undocumented sprawl* + a long tail of raw values.
- **Colors** are the meaningful tokenization target (~4,474 raw). Raw **px**
  (~13,943) are mostly one-off layout/SVG coordinates and should **not** be
  forced into an 8-step spacing scale.

## Findings

1. **`data-studio-models.html` is the healthiest** file (1,026 token defs, 1,381
   `var()` refs) — the right place to pilot the tokenization pattern.
2. **`data-studio.html` and `settings.html` carry the most debt** — future
   burn-down should start there, but only with design review (see #4).
3. **The token layer is sprawling** (526 distinct tokens in the models file,
   incl. pasted-in libraries `--ab-*`, shadcn-style `--accent-foreground`).
   `tokens.css` + `specs/tokens/token-reference.md` consolidate the canonical
   set components should actually use.
4. **Automated color→token replacement is unsafe here.** Of the 101 distinct raw
   colors in the models file, most have no equal-value token (e.g. `#7db1ff`),
   and high-frequency literals like `#fff` (40×) map to *different* tokens
   depending on context (button text vs card bg vs border). Zeroing colors by
   value would cause visual regressions. Burn-down is a per-rule design task;
   the CI script keeps it honest and blocks *new* raw colors.

## Pilot result — `data-studio-models.html`

Scoped color tokenization was attempted on the healthiest file. Outcome: **no safe
automated swaps exist.** Of its raw colors in component rules, **zero** map to an
existing token by exact value — the only exact matches (`#ff6467`, `#fcd34d`,
`#6ee7b7`) are the token **definitions** themselves (Layer 1, correctly raw). The
file is already ~95% tokenized (1,381 `var()` refs); its residual raw colors are
one-off decorative/brand values that should stay raw or get purpose-specific tokens
via design review — not blind replacement. **Net: the models file needs no color
changes; the win here is the tokens/specs/CI scaffolding.**

## Confirming the audit (honest status)

`scripts/token-audit.js` is the source of truth (it strips both token *definitions*
and `var()` usages, so only true Layer-3 raw values are flagged). Current state:

- **Pilot file:** 255 errors / 213 warnings — all pre-existing one-offs (documented above).
- **Project-wide:** 4,244 errors / 1,588 warnings — pre-existing debt, concentrated in
  `data-studio.html` and `settings.html`.

This is **not** zero, and honestly cannot be zeroed safely by automation (see Finding
#4). The script's job is fulfilled: it **blocks new raw values** (zero-tolerance for
new code, per `CLAUDE.md`) and makes the existing debt visible for reviewed burn-down.

```bash
node scripts/token-audit.js                      # whole repo
node scripts/token-audit.js data-studio-models.html
node scripts/token-audit.js --warnings           # also fail on warnings
```
